# 협동 저장 스키마 1–17

## 도적 방 스키마 18

도적을 포함하는 로스터는 18을 쓰며 원래 층의 한도는 floor_schema 1~15가 정한다. 망토·착용자·원본 은신 및 재충전 버프를 같은 Actor와 물리적 물품에 연결한다. 은신 소모까지의 실제 남은 턴을 원본 번들에 보존한다. 가면과 왕관 권리는 해당 정책이 활성인 경우에만 기록한다. [호환성 시험](upper-growth-results.md)

## 전직 및 왕관 시험 저장

일반 방은 기존 층 형식 1~15, 가면 전용 시험방은 16으로 저장한다. 명시적으로 왕관 시험을 켠 방은 17을 사용한다. floor_schema에는 원래 지형 스키마를 보존한다. crown_trial, crown_user, crown_rights는 소비자와 남은 1회 권리를 기록한다. 두 성장 시험을 함께 사용하는 경우 가면 장부도 같은 세대에 저장한다. 변환 전후 갑옷은 동일한 물리적 ID를 사용한다. ClassArmor의 Charger와 반격 대상 Actor ID를 복원한다. 세대 크기 및 휴면 층 제한은 기존 값이다.


## 전직 후보 시험 스키마 16

후보를 선택한 개발 호스트만 schema=16을 쓴다. floor_schema는 원래 저장 구조 1~15 중 하나이며 기존 깊이·분기 한도를 적용한다. mask_trial, mask_user, mask_rights와 영웅의 원본 전직 및 특성을 같은 세대에 저장한다. 일반 세션은 기존 층 스키마에 원본 Hero 특성을 저장한다. SoulMark의 caster_id는 실제 영웅 Actor ID다. 시전자 기록을 복구할 수 없는 표식에는 회복 수혜자를 지정하지 않는다. 다트는 기존 아이템 소유권과 PinCushion의 실물 ID를 쓴다. 세대와 휴면 층 한도는 각각 4 MiB 및 1,500,000 UTF-8 바이트다.

금고 비콘은 스키마 15의 기존 물리적 아이템 저장과 행동 영수증을 사용한다. 두 좌석의 별도 TCP 장애 주입에서 저장 세대 발행 후 응답 유실을 재검증했다. [검증 기록](vault-play-results.md)

스키마 15는 최종 정령 전투를 시작한 활성·휴면 금고 또는 귀환 투표·진행·지상 승리를 보존한다. 세 속성 가중치와 하나의 저주, 아뮬렛 소유권, 최고 귀환 깊이, 기존 영수증을 검사한다. [실행 결과와 다음 작업](vault-ascent-results.md)

스키마 14는 branch 0의 25층 HallsBossLevel과 26층 LastLevel을 추가한다. 이전 스키마 13의 상한은 24층이다. 활성·휴면 보스의 단계·남은 소환·표적 칸·봉쇄와 아뮬렛의 유일성을 검증한다. 아뮬렛 소유자, 제안·계속·최종 동의 및 영수증을 같은 세대로 발행한다. 기존 4 MiB 및 휴면 레코드 1,500,000바이트 한도를 유지한다. [최종 보스·승리 검증 기록](yog-victory-results.md)

스키마 12는 광산과 Imp 금고의 branch/depth를 별도로 보관한다. 금고에서 EscapeCrystal에 파티 지갑 하나, 좌석별 원본 장비 번들과 경로별 ID·소유권을 기록한다. 글로벌 ID 중복은 복원을 거부한다. 스키마 13은 본편 깊이 24까지 확장한다. [Imp 금고와 악마의 전당](imp-halls-results.md)

## 광산·도시 체크포인트

스키마 10은 본편 1~19층과 깊이 12~14 중 실제로 생성된 광산 한 곳을 보존한다. 본편 키는 depth, 광산 키는 1000 + depth다. 한 층만 활성화하고 모든 키의 Actor·실물 아이템 ID를 함께 검사한다. 구버전 1~9의 범위, 4 MiB 세대 및 휴면 레코드당 1,500,000 UTF-8 bytes 제한을 유지한다. [실행 기록](mines-city-results.md) 20층은 스키마 11이다. 봉쇄·원본 왕의 phase와 대기 중인 소환, Ghoul 몸에 남은 활성 버프와 왕관을 보존한다.

## 스키마 8·9 · 동굴과 DM-300

스키마 7 상한 11층, 8 상한 14층, 9 상한 15층이다. 활성 층 하나와 최대 13개 또는 14개 휴면 층을 branch 0에서만 보존한다. 세대 상한 4 MiB, 휴면 레코드당 1,500,000 UTF-8 바이트와 HEAD/BACKUP은 동일하다. 과충전 횟수, 실제 Pylon 방향·진영·고유 ID, 지연 가스의 원래 궤적과 시간, 낙석 버프와 전격 Blob, 봉쇄 및 파편 귀속을 검사한다. 이전 형식에서 존재하던 깊이 제한은 그대로 해석한다. [실제 이전 세대 검증](caves-dm300-results.md)

## 스키마 7 · 감옥 보스방과 동굴 입구

branch 0, 활성 층 1개와 휴면 층 최대 10개, 깊이 1~11. 최초 10층 진입에서 스키마 7로 전환한다. 스키마 6의 상한은 9층이다. 4 MiB 세대·휴면 레코드 1,500,000 UTF-8 바이트·HEAD/BACKUP의 검증 순서를 유지한다. 10층의 START와 FIGHT_PAUSE에서는 별도 Tengu 및 버프 ID를 전역 중복 검사에 포함한다. 전투 단계에서는 동일 ID·HP의 보스가 주민 목록에도 하나 있어야 한다. WON은 보스가 없어야 한다. 봉쇄 플래그와 단계의 조합을 검사한다. storedItems는 물리적 아이템 장부에 포함하며 반환 시 목록을 비운다. 폭탄·전격 장치의 위치·남은 시간과 화염의 방향·셀은 원본 Buff와 Blob의 번들에 보존한다. 양쪽 영웅과 퀵슬롯의 ID는 층 이동으로 재발급하지 않는다.

## 스키마 6 · 감옥 8~9층

처음 8층에 진입하면 세대와 엔진에 스키마 6을 기록한다. 9층까지 활성 층 하나와 휴면 층 최대 여덟 개를 담고 돌아와도 방문 이력을 유지한다. 스키마 5의 최대 깊이는 7이다. 세대당 4 MiB, 휴면 레코드당 1,500,000 UTF-8바이트, HEAD/BACKUP 발행 순서는 계속 적용한다. 강령술사의 소환 셀과 같은 층에 있는 해골·망령의 종류 및 고유 ID, 관계의 중복을 검사한다. 휴면 층의 주문 시전자와 소환수는 활성 스케줄러에 등록되지 않는다. Tengu의 원본 Level 번들 검사는 별도 시험이며 스키마 6의 최대 깊이는 9다.

## 감옥 7층 의뢰 저장

저장 스키마 5와 기존 세대 크기 제한을 사용한다. 원본 Wandmaker.Quest 번들이 종류·수락 상태·두 보상 후보를 보관한다. 의뢰물 소비, 선택한 지팡이의 귀속, NPC 제거 및 행동 영수증은 같은 HEAD에 발행한다. ef88893이 실제 작성한 7층 스키마 5 세대를 새 독립 프로세스에서 읽어 기존 두 좌석과 영수증, 6층 복귀·다음 행동 및 이전 저장본 보존을 검사했다.

## 스키마 5 · 감옥 7층

원본 branch 0의 7층을 처음 확정하면 스키마 5로 발행한다. 활성 층 하나와 최대 여섯 휴면 층, 연속 생성 이력, 이전 깊이로 복귀한 뒤에도 동일한 스키마를 유지한다. 세대당 4 MiB, 휴면 레코드당 1,500,000 UTF-8 바이트, HEAD/BACKUP 2세대가 상한이다. 지원 한도는 스키마 1·2·3·4별로 계속 적용한다. 기준 9b6130f에서 생성한 진짜 스키마 4를 별도 JVM으로 읽어 RNG·아이템·휴면 층·양쪽 좌석·영수증을 비교하고 7층 발행 후 재시작했다.

## 스키마 4 · 감옥 6층

원본 PrisonLevel을 처음 생성하면 엔진과 세대 봉투에 버전 4를 기록하고 5층으로 돌아와도 유지한다. branch 0의 연속된 1–6층, 활성 층 하나와 휴면 층 최대 다섯 개를 같은 세대에 저장한다. 허용 원본 층 타입, 생성 이력, 실제 지형 크기, 모든 층의 Actor·아이템 ID 및 소유권을 검사한다. 4 MiB 세대 한도와 휴면 레코드당 1,500,000 UTF-8 바이트, HEAD/BACKUP 두 세대 정책은 그대로 적용한다. 이전 스키마 1·2·3은 각 버전의 깊이 한도로 읽는다. 6층 진입 전에는 기존 깊이에 맞는 형식을 계속 쓴다.

새 저장의 RoomSync는 좌석별 표시 참조를 재현할 비공개 값을 영수증과 함께 보관한다. 과거 저장에 해당 값이 없으면 최초 복원 시 새 값을 만든다. 실제 퀵슬롯 배치는 클라이언트의 SeatTickets 버전 2에 들어가며 버전 1 티켓도 읽는다. 전체 세대 파일과 티켓은 공개 증거에 포함하지 않는다.

## 하수도 체크포인트의 복원 상태

스키마 3 엔진 이미지의 선택 필드 `documents`는 원본 안내서와 문서의 미발견·발견·읽음 상태를 저장한다. 미발견 항목까지 기록해야 새 JVM에서 이후 층의 원본 안내서 배치 및 방 순서를 재현할 수 있다. 협동 세션 종료 시 기존 Journal 격리 경로가 솔로 프로필 상태를 되돌린다.

원본 다리 방의 `coop_bridge_space`는 아이템·몬스터 배치에서 제외해야 할 영역의 네 경계값이다. 몬스터 `coop_path`와 `coop_alerted`는 확정 시점의 추격 경로와 다음 AI 입력을 보존한다. 경로 길이와 셀은 복원되는 해당 층 범위에서 검사한다. 이전 이미지에서 이 필드들이 없으면 기존 복원 동작을 사용한다. 이 자료는 디스크의 협동 세대에만 저장된다. HEAD 발행, 백업, 영수증, 스키마별 세대 상한은 기존 절차를 따른다.


## 이전 스키마 3 발행 형식

branch 0에서 3층을 처음 생성한 확정 경계부터 스키마 3을 발행한다. 다시 1·2층으로 돌아와도 형식은 3이다. 두 층만 방문한 세션은 기존 스키마 2를 기록한다. 스키마 1과 2의 읽기를 지원한다. 각 세대의 길이, SHA-256, HEAD/BACKUP과 epoch 검사는 기존 방식이다. 행동 영수증과 본문이 같은 파일에 들어간다.

활성 층과 두 영웅은 engine에, 생성했던 나머지 층은 engine.dormant 안의 깊이 키 1–5에 보관한다. 휴면 층은 최대 네 개다. 1–4층은 SewerLevel, 5층은 SewerBossLevel로 검증한다. 활성 층에는 실제 스케줄러 하나가 있다. 휴면 층은 Level 번들, 심도, 양 좌석 탐험, 상대 Actor 시간, 더미·몬스터 보관 아이템의 ID와 소유권을 유지한다. 복원할 때 생성 이력과 층의 연속성, 활성·휴면 전체의 Actor 및 물리적 아이템 ID를 확인한다.

전체 세대 4 MiB, 휴면 층마다 UTF-8 1,500,000바이트, 층당 256×256칸 및 8,192개 휴면 아이템 상한을 유지한다. 실제 이전 바이너리가 만든 비공개 시험 세대의 복사본으로 마이그레이션했다. 스키마 1의 공개 모델 비교는 당시 UI의 아이템 종류 표기로 정규화한다. 물리적 ID와 수량, 원본 스케줄, RNG, 인증키와 영수증은 저장된 필드로도 검증한다. [시험과 측정](sewer-depths.md)

실제 스키마 2를 3으로 발행한 직후 별도 복사본의 HEAD 대상 파일을 훼손했다. 새 호스트의 정상 검사 거부, 명시적 BACKUP 복구, 두 기존 공개키 인증, 새 epoch 발급, 이전 요청 거부와 새 행동 성공을 검증했다.

## 하수도 공통 효과

기존 스키마 1 읽기와 스키마 2 발행을 유지한다. 원본 Level의 함정 활성·공개 상태, 추가 Mob·Blob, Hero의 효과와 Notes의 층별 철 열쇠, 변환된 Item의 고유 ID와 귀속을 기존 저장 경로에서 복원한다. 다트 피해·문 상태·열쇠 차감은 해당 행동 영수증과 함께 HEAD에 발행된다. 4 MiB 상한과 휴면 층 한도는 그대로 적용한다.

스키마 2는 branch 0의 하수도 1·2층을 지원한다. 앱 전용 디렉터리와 HEAD/BACKUP 파일 발행 순서는 스키마 1과 같다. 각 세대는 독립 파일 하나다. 파일 앞의 길이와 SHA-256은 아래 구성 요소 전부를 한꺼번에 검증한다. 층 파일을 다른 세대와 공유하지 않는다.

| 엔진 필드 | 내용 |
|---|---|
| world, guest, schedule, random | 생성 이력·branch/depth·다음 Actor ID, 두 영웅, 활성 Actor 등록 및 입력 차례, 월드 난수 스택 |
| floor, sight0, sight1, items, nextItem | 현재 Level, 두 좌석의 지형 기억, 현 층·가방·장비의 물리적 아이템 ID와 귀속, 세션 단위 발급 상한 |
| parked | 다른 한 층의 branch/depth, 원본 Level, 바닥 더미 순서별 아이템 ID·귀속, 두 좌석의 기억. 아직 다른 층에 방문하지 않았으면 생략 |
| 바깥 세대의 state | 세션·epoch·인증 검증키·잠긴 로스터, State Version, 좌석별 Action ID 상한과 확정 영수증 |

전체 세대는 최대 4 MiB, JSON 깊이 최대 64, 비활성 층 레코드는 최대 1,500,000 UTF-8 바이트다. 맵은 층마다 최대 256×256칸, 비활성 층의 아이템은 최대 8,192개다. 정상 상태에서 두 세대를 보존하고 발행 중 임시 세대가 하나 추가될 수 있다. 따로 발행할 층 파일이나 층별 참조 수명은 없다. 손상된 현재 세대의 일부를 백업 세대에 끼워 넣을 수 없다.

한 층을 떠날 때 원본 beforeTransition의 부분 턴 정리를 각 영웅에게 적용한다. 그 뒤 활성 Actor의 기준 시각을 빼고 경과 시간을 Statistics.duration으로 옮긴다. 떠난 층의 몬스터·버프·스포너는 등록되지 않은 원본 Bundle로 보관한다. 돌아올 때 원래 ID, 상대 지연과 공격 대상을 되살린다. 두 영웅은 하나씩 등록하며 현재 층에만 시야와 전투 경계를 재계산한다. 동의는 연결 및 입력 턴에만 유효하다. 영수증이 남아도 재접속시 동의가 자동 복원되지 않는다.

스키마 1의 길이·해시·세션·세대·엔진 값이 유효하고 원래 저장 범위에 속하면 기존 로스터와 RNG로 복원한다. 새 스키마의 첫 세대는 잠긴 두 좌석을 검증한 뒤 발행한다. 원래 세대는 이전 HEAD로 보존한다. 원본 알파와 새 호스트를 별도 JVM에서 실행하는 검증 스크립트는 BUILD.md에 있다. 저장된 RNG 스택 복원과 이후의 모든 무작위 실행에 대한 완전한 재현성은 구별한다.

## 기존 협동 저장 형식 1

호스트의 앱 전용 저장 경로는 `coop-saves-v1/<세션 UUID>/`이다. 엔진 실행 스레드가 다음 입력권 확정 직후 또는 파티 전멸 경계에서 저장한다. 행동 처리 중이거나 엔진이 비정상 정지한 상태, 직렬화할 수 없는 임시 Actor가 등록된 상태는 저장을 거부한다. 지원 범위는 도전 옵션이 없는 branch 0, depth 1이다. 저장 스키마와 원본 게임 버전을 함께 검사한다.

## 엔진 이미지

원본 Dungeon Bundle은 첫 영웅, 생성 상태, 통계와 다음 Actor ID를 담는다. 두 번째 영웅과 실제 Level도 같은 이미지에 각자의 원본 Bundle로 저장한다. 복원할 때 두 영웅에게 시작 장비를 다시 지급하지 않는다. Actor ID를 기준으로 원본 클래스, 우선순위, 시간, 동결 상태를 검증한다. Level에 몬스터와 버프를 등록한 다음 게임 시계와 현재 입력 Actor를 복구한다. 전투 불능 Actor는 부활까지 남은 상대 시간을 보존한다.

좌석마다 visited·mapped 비트셋과 마지막 관측 지형을 저장한다. 복원된 맵에서 직접 시야와 전투 구역을 다시 계산한다. 아이템 표에서 가방·장비의 순회 위치 또는 바닥 더미의 셀과 순서, 클래스, 수량을 검사하고 원래 내부 ID와 귀속자를 연결한다. 소비·병합으로 사라진 객체는 생성하지 않으며 다음 ID 발급 상한을 유지한다. 같은 저장 세대에 있는 영수증 및 공개 핸들 처리 규칙은 [재접속 명세](reconnect.md)에 있다.

Java Random과 같은 선형 합동 생성기의 48비트 내부 상태를 스택 순서대로 저장한다. 복원 직후 스택 상단의 다음 추출과 pop 이후 바깥 생성기의 다음 추출을 비교하는 테스트가 있다. 이후 새로 만드는 비시드 생성기, 순서가 지정되지 않은 컬렉션 및 플랫폼 차이를 포함한 장기 결정적 리플레이에는 별도의 검증이 필요하다.

## 파일 발행과 롤백

각 세대 파일은 4바이트 big-endian 길이, SHA-256 32바이트, 비압축 UTF-8 JSON Bundle로 구성된다. 봉투에는 스키마·세션 UUID·세대 번호·상태 본문이 들어간다. 본문을 포함한 JSON 한도는 4 MiB이며 중첩 깊이는 최대 64다. 이 파일은 호스트 앱의 전용 로컬 저장 데이터다. LAN에는 좌석별 공개 모델만 보낸다.

1. 한 호스트가 세션 디렉터리의 OS 파일 잠금을 획득한다. 다음 백업이 될 기존 세대의 길이·체크섬·식별자를 검사한다.
2. 임시 파일에 새 세대를 쓰고 파일 디스크립터를 동기화한다. 다시 읽어 검증한 뒤 같은 디렉터리에서 세대 파일로 이름을 바꾸고 디렉터리를 동기화한다.
3. BACKUP에는 이미 발행한 이전 세대를 복구 후보로 기록한다. HEAD에는 새 현재 세대와 이전 정상 세대를 기록한다. 두 포인터 모두 번호와 비트 반전값을 함께 저장하며 임시 포인터를 동기화한 후 rename과 디렉터리 동기화를 거친다.
4. HEAD 발행이 끝나야 정상 확정 영수증을 전송한다. 발행 전 끊긴 임시 세대는 진행 기록으로 선택하지 않는다. 다음 저장에서 임시 파일을 덮어쓰고, 다시 열 때 관리 대상 파일 중 두 참조 세대 밖에 있는 파일을 정리한다.
5. 현재 세대가 잘리거나 잘못된 경우 정상 재개를 거부한다. HEAD가 누락되거나 손상된 경우 독립 BACKUP 포인터로 이전 세대만 선택할 수 있다. 호스트가 명시적으로 복구를 선택하면 검증된 이전 상태를 새 세대와 새 epoch로 발행한다. 두 포인터나 두 후보 세대가 모두 손상되면 복구를 중단한다.

Linux JVM 테스트는 파일 기록, 검증, HEAD 교체 전후에서 자식 프로세스를 강제 종료한다. Android 경로는 android.system.Os로 디렉터리를 동기화한다. 실제 Android 저장소의 정전 내구성과 모바일 저장 지연은 실기기 검증 항목이다.

## Phase 8 UI

앱은 CoopSaves.sessions/inspect로 정상·손상·백업 상태를 표시하고 선택한 세대를 확인한 뒤 resume을 호출한다. 스키마 1의 데이터 배치는 동일하다.

감시탑의 원본 room, initial_delay, cur_delay와 함께 협동 충전 중인 표적 Actor ID를 coopTarget에 기록한다. 필드가 없으면 미조준으로 읽는다. 같은 세대의 스케줄러가 발사 시간을 결정한다. 피라냐는 원본 Mob의 위치·HP·상태·표적 저장 경로를 사용한다.

2층 유령 퀘스트는 스키마 2의 world 안에 있는 원본 sadGhost 번들에 생성 여부·층·수락·처치·보상 후보를 저장한다. 수령 후 후보를 비우고 유령을 제거한다. 받은 실제 Item의 내부 ID·소유 좌석, 퀘스트 상태와 해당 행동의 영수증은 같은 HEAD 세대로 발행된다. 이전 호스트가 추가 Actor와 영수증을 이해하지 못하므로 새 빌드에서 진행한 저장본의 이전 APK 다운그레이드는 지원하지 않는다.

객체별 coopBee(Actor ID)는 협동 깨진 꿀단지와 해당 벌을 연결한다. 원본 potPos와 potHolder는 현재 층의 방어 위치·표적을 저장한다. 휴면 층에는 벌을 등록하지 않는다. 재방문 때 활성 층의 실제 가방·바닥 조각을 확인한다. 담긴 층이 다르면 벌이 옛 소유자를 계속 공격하지 않는다. 서로 다른 벌을 가리키는 조각은 쌓지 않는다.

일반 미믹의 원본 items 배열은 Actor ID와 배열 인덱스에 대응하는 m<actor>_<index> 소유권 레코드를 사용한다. 활성 층과 휴면 층을 합쳐 내부 ID 중복, 수량 및 원본 클래스 일치를 검사한다. 기존 출시 체크포인트는 미믹을 허용하지 않았다.

수정 미믹의 탈취는 피해자 가방에서 한 단위를 detach한다. 분할 시 새 내부 ID에 같은 소유자를 기록하며, 수량 1인 객체는 같은 ID로 이동한다. 보유자 Actor ID와 배열 위치가 저장된다. 처치 시 원본 Heap으로 이동하고, 도주 성공 시 그 보관품은 월드에서 함께 사라진다. 스택 합류로 소비된 ID를 재발급하지 않는다.

## 석상 장비와 세대 무결성

스키마 2 안에서 w<ActorID>는 석상이 보유한 원본 무기 한 개를 가리킨다. 실제 무기·강화·저주·인챈트는 원본 Statue Bundle에, 내부 ID·소유자·수량·클래스는 같은 세대의 물리적 위치 목록에 기록한다. 활성 층·휴면 층 양쪽의 Actor/아이템 ID 범위와 중복을 확인한다. 처치 후에는 같은 무기가 바닥 위치로 이동한다. 지원했던 스키마 1·2의 기존 저장 회귀를 유지한다. 층 한도와 세대 크기 제한은 기존 값이다.

### Prison merchant custody

Schema 4 keeps the shared gold in the native world bundle and the latest three sold objects in Shopkeeper.buyback_items. Each physical object there has an ownership entry keyed by shop, the keeper's Actor ID and its list index. On load the item class, quantity, original owner and unique physical ID are checked against that same generation. Dormant records use the same location convention. New code can read earlier schema 4 worlds with empty merchant histories.

### Projectiles held by monsters

A supported knife in PinCushion stays in the original buff's items array. Its owner and physical ID are recorded as pin<monster ID>_<array index>. Both active and dormant object walks use that ordering. A surviving missile may merge only with a compatible stack belonging to the same owner. Native death/drop and native durability decide whether a floor object exists. The renderer receives no list of projectiles hidden in monsters.

# SYNC38 Android 인수

두 Android 15 MuMu에서 3be69c306edcf97f5ee6670563181b0a300586fe 빌드를 데이터 보존 업데이트했다. 각 기기의 Chromium에서 비로그인 다운로드했고 설치된 두 base.apk는 모두 35,421,948바이트, SHA-256 `5c03e43a4fbf7d1035f3e7920050e79b2a4a4f5834251a04957c610e5048b199`이었다. 패키지는 org.spdcoop.dungeon.indev, versionCode는 922다. 개발 인증서 SHA-256은 `0dd9070b5f17192a8b07e5ddb6735161b0d2bb6e49013e4d61ca5ee6216ddb53`이다.

이전 배포판은 classes2.dex의 0x63에서 Object[]를 Bundlable[] 필드에 저장하려다 ART 검증에 실패했다. SYNC38은 명시적으로 배열 형식을 지정해 복사한다. 실제 DEX의 check-cast 0x6a와 iput-object 0x6c를 검사했다. 이전에 멈춘 격리 시험방에서 원래 방장이 다시 주문서를 읽었고, 두 앱을 재시작한 뒤에도 불타는·불안정한·짜릿한 세 후보가 유지됐다. 확정 영수증에서 상태 버전이 17에서 18로 증가했고 재접속 뒤 두 좌석의 WAIT도 확정됐다.

신규 격리 방에서는 두 좌석이 직접 바닥의 주문서를 획득했다. 미감정 주문서는 읽을 때, 감정된 주문서는 장비를 선택해 후보를 뽑을 때 소비됐다. 예를 들어 방장의 첫 묶음 ID 28에서 소비한 단위는 31이었다. 게스트의 후보를 생성할 때 원래 묶음은 30, 소비 단위는 32, 대상 장비는 25였다. 상대 화면에는 후보 선택창이 나타나지 않았다.

중복 요청과 오래된 요청의 시험은 이번 작업에서 새로 등록한 시험용 두 좌석으로 Android 권위 호스트에 정상 인증해 수행했다. 격리 방의 이전 세대 복구 후 각 좌석의 ENCHANT_CHOOSE 7번을 그대로 다시 보냈다. 각각 기존 RESULT 7의 확정 상태 버전 14와 17을 그대로 돌려받았다. 새 요청 번호로 같은 오래된 입력을 전송하자 두 건 모두 현재 버전 20에서 REJECT_VERSION을 반환했다. 실제 앱으로 다시 인증한 뒤 양쪽 WAIT가 확정됐다. 시험 세션의 가장 마지막 HEAD와 상태 버전은 모두 25였다.

부팅 ID는 방장 `7867132f-4ba4-4a71-abe0-b096e52cdc07`, 게스트 `8ce63420-1712-4ee2-a895-b5568acebf55`였다. 두 기기의 패키지 로그와 ANR 이벤트, 시험 좌석의 요청 대기열, 저장 세대 체크섬을 확인했다. 시험 중 관측한 VerifyError·LinkageError·치명적 GLThread 예외·프로세스 크래시·ANR·호스트 응답 중단·확정 영수증 누락은 각각 0건이었다. 각 시험 좌석의 최종 대기 요청 수도 0이었다.

실행 환경은 Windows 루프백 ADB 중계와 격리된 배치형 시험방이다. 실제 휴대폰 Wi-Fi·핫스팟·정상 시작 캠페인은 이 인수의 범위 밖이다. 기존 SYNC37의 실패 기록은 [이전 Android 보고서](enchantment-android-acceptance.md)에 있다. 검사기 입력, 체크섬을 대조한 영수증, 화면과 기기 로그 집계는 Cloud 인수 자료에 보존했다.

## 추가 성장 시험에서 발견한 실패

게스트 성직자가 성서에서 정지를 선택하면 충전이 5에서 3으로 줄고 스키마 25에 LightAlly가 저장됐다. 소환수 Actor 21, HP 80/80, PowerBuff 소유자 15, 보호막 24를 확인했다. 두 앱을 재시작하고 같은 좌석으로 복귀한 뒤, 게스트 차례에 성서를 열었을 때 정지 항목이 사라졌다. 무료 수동 해제 및 그 경로의 다음 영수증은 FAIL이다. 크래시나 ART 예외는 없었다. 실제 기기의 증상은 저장된 소환수가 있을 때도 활성 소환수만 검사하던 주문 선택창 조건과 일치한다. SYNC38의 주문서 수정은 통과했으며 전체 인수와 대응 ZIP 발행은 보류했다.
